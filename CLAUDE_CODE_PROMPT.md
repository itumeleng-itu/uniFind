# Claude Code build prompt — uniFind

Copy everything below the line into Claude Code in an empty `uniFind` directory.

---

Build uniFind: a Next.js + TypeScript service that helps South African matric
learners find university courses they qualify for, free, and sells one paid
add-on — an AI-written admissions report at R79 — generated by Gemini on
Vertex AI. The course catalogue and bursary list are maintained by scheduled
agents rather than by hand.

Stack: Next.js 15 (App Router), TypeScript strict, PostgreSQL via `pg`,
Vertex AI via `@google/genai`, Paystack for payments, Cloud Run + Cloud Run
Jobs + Cloud Scheduler for hosting.

## Non-negotiable invariants

Restate these back to me before you start, and re-check them at every phase
gate. If a phase would break one, stop and tell me instead of working around
it.

1. **Nothing unverified reaches a paying customer.** Programmes and bursaries
   carry a `status` column. Only rows at `'verified'` may be used to ground a
   paid report. The model selects and explains from supplied rows; it never
   recalls a bursary, an institution, or a points requirement from training.
2. **The payment webhook is idempotent.** Paystack retries on any non-2xx.
   The same reference delivered five times must produce exactly one report.
3. **Agents escalate below a confidence threshold rather than writing.**
   Every agent decision is logged before it is applied, with the model's
   confidence and rationale, and whether a human ever touched it.
4. **Closed programmes are never recommended.** Filter on the effective
   deadline in the query, not in the prompt.
5. **Every Gemini call is logged to `cost_events`.** The P&L is queried, not
   estimated, so no inference may happen outside the one wrapper.
6. **No secrets in the repo.** `.env` is gitignored; production reads from
   Secret Manager.

Before Phase 1, install `@electric-sql/pglite` as a dev dependency and set up

## Phases

**Phase 1 — schema.** `db/migrations/0001_core.sql` and `0002_agents.sql`.
Tables: institutions, programmes, programme_subject_requirements, bursaries,
students, match_runs, payments, reports, cost_events, agent_runs,
agent_decisions, support_tickets. Plus an `agent_autonomy_daily` view
computing decisions / applied / escalated / overridden / autonomous_pct.

Key constraints: `unique (provider, reference)` on payments and a unique
index on `reports(payment_id)` — these two are what make the webhook
idempotent, so never drop them.

*Gate:* migrations apply cleanly; every table present.

**Phase 2 — admissions reality.** `0003_admissions_reality.sql`. Adds
`scoring_system` to institutions (`aps`, `uct_fps`, `stellenbosch`, `rhodes`,
`nbt_composite`, `open`), a `faculty_deadlines` table, and an
`open_programmes` view exposing the effective closing date as
`coalesce(faculty_deadline, institution_deadline)`.

*Gate:* seeded closed programme is excluded; open one is returned.

**Phase 3 — lib.** `src/lib/env.ts` (fail fast on missing vars),
`db.ts` (small pool — Cloud Run scales horizontally), `vertex.ts` (single
`generate`/`generateJson` entry point that writes token usage to
`cost_events`), `paystack.ts` (initialise, verify, refund, and HMAC-SHA512
signature verification).

*Gate:* typecheck clean; signature verification unit-tested against a known
HMAC.

**Phase 4 — payments.** `POST /api/checkout` creates the pending payment row
*before* redirecting. `POST /api/paystack/webhook` verifies the signature,
re-reads the transaction from Paystack rather than trusting the body, marks
paid, inserts the report with `on conflict do nothing`, and returns 200 even
for duplicates and unknown references.

*Gate:* assertion proving three deliveries of one reference produce one
report, and an unknown reference produces nothing.

**Phase 5 — report generation.** `src/reports/prompt.ts` and `generate.ts`.
`assembleInput` pulls only verified, still-open rows and builds three lists:
qualifies-for, narrowly-missed, already-closed. Order matches by closing date
ascending — a deadline is more urgent than a fit. Claim the row with a
conditional UPDATE so two workers can't generate the same report. Store the
full input snapshot, model name, and token counts alongside the output.

The prompt must instruct the model that any institution with a non-APS
scoring system calculates its own score and the learner's APS is indicative
only.

*Gate:* assertion that an unverified programme and an expired bursary do not
appear in assembled input.

**Phase 6 — agents.** `src/agents/base.ts` exposes `runAgent()` and
`AgentRun.decide()`. `decide()` writes the decision row, applies the change
only above threshold, and marks it escalated otherwise.

Then three agents: `course-sync` (discovers each institution's prospectus URL
from its homepage, extracts programme requirements, diffs against the
catalogue, decides insert / update / withdraw), `bursary-verify` (re-reads
each bursary's live page, promotes or expires), `support` (triages tickets,
regenerates reports, issues refunds under a ceiling). Plus `runner.ts` as the
Cloud Run Jobs entrypoint.

Mark `withdraw` decisions deliberately below threshold — a programme missing
from one page load is usually a rendering quirk, and removing a real course
from a learner's results is the worse error.

*Gate:* assertion that a below-threshold decision is recorded but not
applied, and `agent_autonomy_daily` computes the right percentage.

**Phase 7 — report page.** `/r/[token]`. No client JS, no webfonts, no
images — the reader is on a mid-range Android paying for their own data.
Escape the markdown before rendering; the report echoes learner-supplied
interests.

**Phase 8 — deploy + evidence.** Dockerfile (standalone Next output, one
image for web and jobs), `cloudbuild.yaml`, and `sql/submission_evidence.sql`
with P&L, unit economics, funnel, and agent autonomy queries.

*Gate:* every evidence query runs against seeded data.

## Traps — I have hit all of these

- **No `citext`.** It needs an extension Supabase and Cloud SQL don't enable
  by default. Use `text` and lowercase emails at write time.
- **P&L double-counting.** A refunded sale *was* collected. Count
  `status in ('paid','refunded')` in gross revenue, then reverse the refund
  out on its own date. Excluding it from revenue *and* subtracting it charges
  the same R79 twice.
- **`timingSafeEqual` throws on length mismatch.** Compare buffer lengths
  first or an invalid signature 500s instead of 401s.
- **Paystack channels.** For South Africa use `["card","bank_transfer"]`.
  Instant EFT and Capitec Pay need a separate KYC review, and mobile money
  and USSD are not SA channels — listing them breaks checkout.
- **Deadline filter belongs in SQL.** A prompt instruction not to recommend
  closed programmes will eventually be ignored. The query must not return
  them.
- **Cost logging must never break a paid report.** Catch and swallow failures
  in the `cost_events` insert.
